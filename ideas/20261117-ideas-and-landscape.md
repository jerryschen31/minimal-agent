# Ideas & landscape — 2026-11-17

## TL;DR

- Nothing new has shipped. `origin/build` still ends at PR #42, and the newest commit on `feat/autonomous-mode-2` is `b0d8573` (2026-11-10). Seven days without work toward the thesis (durable, auditable, measurable runs). The 11-16 recommendation stands: build the canary-exfiltration eval first.
- New fact from AWS's Compute Blog: Nitro Sandboxes have **two modes**. *Isolated* (own VM and kernel, but the node operator is still trusted) and *confidential* (attestable, encrypted ephemeral layer, protects you from your own operators). A `profile` of just `local | sandboxed` is too coarse; regulated users will ask which of the two they are in.
- New idea: **the plan file is the egress manifest.** `plan/` already has a `gate` field and an "Accept this plan?" step. Let each task declare the hosts and credentials it needs; accepting the plan approves the network policy for that run, and anything else is denied or asked.
- New idea: replace glob `denyRules`/`askRules` with a small policy language (Cedar or CEL), because regulators want policy that is data, versioned, hashed into the run manifest and checkable. Also borrow Invariant's "tool A output then tool B call" rules as the form of the lethal-trifecta check.
- Landscape: eight projects not covered before (Kubernetes agent-sandbox, OpenSandbox, Vercel Sandbox, OpenAI Agents SDK sandbox agents, Cedar, Invariant Guardrails, Betterleaks/gitleaks, plus Nitro details).

## Part 1 — Direction under "the sandbox is the boundary"

Earlier reports covered the delete/demote table (11-15), the `Sandbox` interface and harness-owned shell state (11-16), snapshot traps, exact-value DLP and taint through summaries. I do not repeat them. Four new angles.

### 1. The threat model decides where the harness lives

The 11-15 report recommended the harness *outside* the sandbox as a control plane. The Nitro blog adds a case where *inside* is right. In **confidential** mode the parent instance is untrusted, the hypervisor hides sandbox memory from it, and KMS key policies can require specific attestation measurements before releasing a key ([AWS Compute Blog](https://aws.amazon.com/blogs/compute/nitro-sandboxes-hardware-isolation-for-every-eks-pod-ecs-task-and-ec2-workload/)). If the operator is the adversary, a control plane on the operator's node is no more trusted than the data. The harness, model key and journal then belong inside the attested sandbox, with the key released only after attestation. So:

| Mode | Who you distrust | Harness | Provider key |
|---|---|---|---|
| `local` (laptop) | the model | in process, today's guards | env/config |
| `isolated` | the model | outside, runs tools through exec API | stays outside |
| `confidential` | model **and** operators | inside the sandbox | released by attestation, then used via egress proxy |

Downside: three profiles triple the test matrix. Mitigation: the `Sandbox` interface from 11-16 is the same; only where `main.go` runs changes.

### 2. Policy as data, not globs

`hooks.ToolRules` matches globs over tool names and `run_command:<glob>` command lines; its own docs say "a glob over a command line is not a detector." In a sandbox the thing to govern is an *effect* (egress, credential use, external write), which has structure: method, host, path, handle, task. A policy language fits that. Nitro's confidential mode itself gates image loading and runtime operations with a Cedar policy (same AWS post). Cedar is a Rust authorization language with a default-deny quick start, designed to be analyzable ([GitHub](https://github.com/cedar-policy/cedar)); I did not find Go bindings on the page, so for a Go kernel check CEL or a hand-rolled matcher. The point is the *shape*: `permit(principal=task, action=egress, resource=host)`; policy file hash goes into the run manifest ("agent lockfile"); "why was this denied" becomes a policy id in the journal. First slice: keep globs, but make the *input* a typed event `{kind, method, host, path, handle, task}` so the engine can change later.

### 3. The plan is the egress manifest (new, uses existing code)

Plan mode writes `<name>.plan.md` and asks "Accept this plan?". Add per-task `needs:` lines (hosts, credential handles, writable paths), generated by the planner and checked by Go. Accepting the plan approves the run's egress allowlist and handles; at run time anything outside a task's `needs` is `deny` (or `ask` for a handle). This is the Terraform-style plan/apply already in `PLAN-plan-apply.md`, applied to the network. Who benefits: regulated teams, who can review one document before a run and attach it to the audit record. Differentiation: Claude Code and Codex ask per action; a reviewed per-task manifest is closer to change control. Downside: planners guess wrong hosts (a package mirror, a redirect), so the first runs need a "report" mode (log, don't block; Smokescreen's rollout idea from 11-15) to calibrate.

### 4. A measurable eval matrix

11-15 and 11-16 proposed one canary eval. Make it a matrix, since a single case only shows that one defence works once:

- **Attacks:** plain POST to evil host; canary base64/hex/split; exfil via an *allowed* host (a gist, an issue comment); DNS lookup of `<canary>.evil.example`; injection arriving through a file the agent reads, not a web tool; injection through a compaction summary.
- **Defences:** none; taint-escalation; exact-value DLP; per-task egress manifest; the Invariant-style flow rule.
- **Metrics:** canary leaked (bool), real task completed, number of false blocks, extra human asks. Report *utility under attack*, as AgentDojo-based papers do (the CaMeL figures in 11-15: 77% vs 84%).

This is the first real measurement the project could produce, and it needs a fake provider and a logging `http.Transport`, no sandbox.

## Credentials & data leakage

A sandbox protects the host, not the secrets in it. New ranked ideas (earlier lists: 11-15, 11-16 still apply):

1. **Credential use is a first-class journal event.** Every injection by the proxy or handle resolution writes `cred_used{run, call, handle, host, token id, scope, expiry}` and never the value. Tamper-evidence of *use* is what an auditor asks for. Plug in: `trace` event type plus `state/`.
2. **Scan what comes *in*, not only what goes out.** A repo inside the sandbox may hold `.env` or keys that `read_file`'s deny list would have hidden on the laptop. In the sandboxed profile the deny list is gone, so run the `Detector` over *tool output before it enters memory*, and replace hits with `[REDACTED:rule#hash]` (stable, so the model can compare values). Candidate engine behind `trace/redact.go`'s `Detector`: **Betterleaks** (Go, MIT, from the Gitleaks author, has a Go library API per its README as summarized by [Help Net Security](https://www.helpnetsecurity.com/2026/03/19/betterleaks-open-source-secrets-scanner/)). Gitleaks itself says it is feature complete with security patches only, and points to Betterleaks ([GitHub](https://github.com/gitleaks/gitleaks)). Downside: scanners flag high-entropy test data; keep the existing rules as the default and make scanner use opt-in.
3. **Trifecta as a flow rule.** Invariant Guardrails expresses "this tool's output fed a later call" (their example: read inbox, then email an unknown address) as a rule over the trace ([GitHub](https://github.com/invariantlabs-ai/invariant)). Same shape as a `BeforeTool` hook that reads memory: *if any message since the last `user` turn has label `untrusted` and the pending call's egress target is not in the task's `needs`, return `ErrNeedsApproval`.* Combined with idea 3 above, this breaks the "way out" leg without parsing shell commands.
4. **Short-lived credentials are bound to the task, not the run.** The control plane mints a token per task (GitHub App installation token, STS role) with the scope from `needs:`, and revokes it at the task boundary. A leaked token then dies when the task ends. In confidential mode, release the minting key only to the attested sandbox.
5. **Per-task egress policy with a report mode first.** Deny by default in the end state; start in log-only to learn what a task really contacts, then promote the log to the manifest.
6. **Detect, don't just prevent.** Plant a canary in env and a file in every eval run (and, for CI, a Canarytokens AWS key from 11-16). Alert on any appearance in proxy logs, journal, or model output.

**Mapping to minimal-agent:** 1 → `trace` + `state/`; 2 → `trace/redact.go` called from `executeToolCall` before memory append; 3 → a `hooks` hook with access to message labels; 4 → config + tool wrapper; 5 → `config` keys plus the proxy; 6 → eval.

**First slice (about 150 lines, hand-writable):** a `Detector` wrapper called on tool output before it enters memory, plus a label on `model.ChatMessage` (`untrusted bool`) set for MCP and web results, plus the hook in idea 3. Test: fake tool returns an injection naming an *allowed* host and a base64 canary. Pass if the call becomes `ErrNeedsApproval`, the canary never reaches the model unredacted, and a clean control run is not blocked.

## Recommendation

Same as 11-16, now sharper: **build the eval matrix with two attacks first** (plain POST, and exfil via an allowed host), against *no defence* and *taint+flow-rule hook*. It needs no sandbox, it finishes the project's first measurement, and the allowed-host case shows whether per-task manifests (idea 3) are worth building. Candidly: the sandbox ideas are interesting but the repo has produced no run in a week; a measured eval is smaller than any of them and moves the thesis.

## Part 2 — Landscape (stars observed 2026-11-17 on the pages fetched)

Not repeated: everything in the 11-15 and 11-16 reports.

**1. AWS Nitro Sandboxes (revisit).** New details: confidential vs isolated modes; Cedar-gated image loading; network policies and security groups enforced on the parent outside the sandbox; no extra charge; EKS uses `runtimeClassName`; the post says nothing about snapshots, quotas or egress rules ([AWS blog](https://aws.amazon.com/blogs/compute/nitro-sandboxes-hardware-isolation-for-every-eks-pod-ecs-task-and-ec2-workload/)). *Lesson:* treat "confidential" as a profile you must detect, and write the attestation into journal entry 0.

**2. Kubernetes agent-sandbox (Apache-2.0).** 4.6k stars. A Kubernetes SIG Apps project: a `Sandbox` CRD for single-pod, stateful, long-running workloads with a stable hostname, persistent storage, pause/resume; extensions `SandboxTemplate`, `SandboxClaim`, `SandboxWarmPool`; delegates isolation to gVisor or Kata via `RuntimeClass`. Release date unverified; network policy and snapshots not described on the page ([GitHub](https://github.com/kubernetes-sigs/agent-sandbox)). *Lesson:* the Template/Claim split (what a sandbox is vs one task's request for it) maps onto "image digest in the manifest" vs "this task's `needs:`".

**3. OpenSandbox (Alibaba, Apache-2.0).** About 17.5k stars; an Agentic AI Foundation project. Docker locally, Kubernetes at scale; SDKs in Python, Java/Kotlin, TypeScript, C#, Go; per-sandbox egress policy, a `osb` CLI, an MCP server and a "Credential Vault" so agents call services without real credentials in the workload. Firecracker "Fast Sandbox" runtime with pause/resume and 64 ms P50 creation (their figure, unverified); no release listed ([GitHub](https://github.com/alibaba/OpenSandbox)). *Lesson:* it is the one open project with a Go SDK, egress policy and a credential vault together; read its egress-policy format before inventing one.

**4. Vercel Sandbox (Apache-2.0 SDK).** 225 stars on the SDK repo; Firecracker microVMs; persistent by default (filesystem saved on stop, restored on resume). The page does not describe network policy or credential brokering ([GitHub](https://github.com/vercel/sandbox)). *Lesson:* "persistent by default" is a different durability stance than a throwaway sandbox; decide which your journal assumes.

**5. OpenAI Agents SDK sandbox agents (MIT).** 30.7k stars. Agents "preconfigured to work with a container … over long time horizons"; a `Manifest` of entries (e.g. a `GitRepo`) declares the workspace; clients `UnixLocalSandboxClient` and `DockerSandboxClient` shown, with the client supplied per run via `RunConfig`; the page showed no snapshot mechanism ([GitHub](https://github.com/openai/openai-agents-python)). *Lesson:* the Manifest is a ready-made name for "declare the workspace up front"; your task `needs:` extends the same idea to network and credentials.

**6. Cedar (Apache-2.0).** About 1.9k stars; Rust; default-deny, analyzable, WASM build; no adopters listed on the page ([GitHub](https://github.com/cedar-policy/cedar)). *Lesson:* see Part 1, item 2. Honest downside: a Rust dependency in a "one dependency" Go project.

**7. Invariant Guardrails (Apache-2.0).** 477 stars; rule layer between an app and its MCP servers or LLM provider; Python-like rules over message traces, including tool-output-to-tool-call flows; usable as a gateway or a `LocalPolicy` in Python ([GitHub](https://github.com/invariantlabs-ai/invariant)). *Lesson:* the *rule shape* for the trifecta; reimplement the idea in Go as a hook, not the dependency.

**8. Betterleaks and Gitleaks (MIT).** Gitleaks: 31.1k stars, Go, CLI with a `stdin` mode, now security-patches-only ([GitHub](https://github.com/gitleaks/gitleaks)). Betterleaks: Go, MIT, successor by the same author, supports Git, GitHub, GitLab, Hugging Face and S3 sources; third-party star counts disagree (one listing ~1.4k, another 712), so **unverified** ([search summary](https://www.helpnetsecurity.com/2026/03/19/betterleaks-open-source-secrets-scanner/), [repo](https://github.com/betterleaks/betterleaks)). *Lesson:* a Go library can sit behind `Detector`; shelling to the CLI's `stdin` mode is the zero-dependency alternative.

### Takeaways

- Sandbox runtimes are converging on three features: pause/resume, per-sandbox egress policy, and a credential vault (OpenSandbox lists all three). Vercel and the Kubernetes project do not show egress or credentials on their pages.
- The orchestration layer is separating "what a sandbox is" (template, manifest) from "this task's claim." Your plan file can be the claim.
- Still no one in this list pairs a *reviewed per-task policy* with a *signed journal that outlives the sandbox*.
