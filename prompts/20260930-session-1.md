  and § "MCP protocol version"). Here is how they fit together for step 3.

  The one idea

  The loop doesn't change. It only knows Tool, with GetToolDefinition() and
  CallTool(). An MCP server is a factory for Tools. You connect, ask it what
  tools it has, and wrap each one in a small struct that satisfies Tool. Then
  you Register those into the same ToolRegistry. reActLoop, runToolCall and the
  registry stay untouched.

  The pieces

  Config.MCPServers ──► setupToolRegistry ──► connectMCP(cmd, args)   (one per 
  server)
                                                │ spawn process, probe/handshake
                                                ▼
                                           *mcpClient ──ListTools()──► []Tool 
  (mcpTool per entry)
                                                ▲                          │
                                                └── mcpTool.CallTool ◄─────┘ 
  registered in ToolRegistry

  1. Transport (stdio JSON-RPC). Start the server as a child process. Write one
     JSON message per line to its stdin and read one per line from its stdout.
     This is the hardest part to get right.
     - Request/response matching. Tool calls can run concurrently, so you need a
       read goroutine. It routes each reply to the right caller by id, using a
       map[id]chan.
     - Write lock. A mutex serialises writes to stdin.
     - Server death. If stdout closes, fail every waiting call instead of
       hanging.
  2. Handshake (3a modern, 3b legacy). This is what DECISIONS.md already
     settles:
     - Send server/discover with _meta. A reply means modern.
     - Any other error or a timeout means fall back to initialize followed by
       notifications/initialized.
     - Record which era the server is, because every later request depends on
       it.
  3. tools/list → []Tool. Each entry has a name, description and inputSchema.
     The schema is already JSON Schema, so it maps straight onto
     NewToolDef(name, desc, schema). Name the tool <server>_<tool>. That avoids
     collisions, and Register already rejects duplicates.
  4. mcpTool.CallTool. Send tools/call with {name, arguments}. Then flatten the
     reply's content[] into a string and keep the text parts. If isError is
     true, return it as an error so the existing "failure becomes an
     observation" path handles it. Truncate big outputs.
  5. Lifecycle. The child process must not outlive the agent. Use
     exec.CommandContext, close stdin on shutdown, and put the cleanup in
     gracefulShutdown, which already exists.
  6. Config. Add something like MCPServers []MCPServerConfig{Name, Command, 
     Args, Env} next to Tools. In setupToolRegistry, connect each server and
     register its tools where the // later we will add MCP tools comment is.

  2. Do legacy servers need the client to hold state?

  Yes, but the SDK holds it for you. You don't need extra state structs.

  For a legacy server, the connection is a session:
  - The handshake (initialize → response → notifications/initialized) happens
    once per connection. The client and server agree on a protocol version and
    exchange their capabilities.
  - Both sides remember that for the life of the connection. For stdio, that's
    the life of the child process. For HTTP, the server may also issue a session
    ID header that the client must send back.
  - If the process dies, the session is gone. You must restart it and handshake
    again.

  The 2026-07-28 revision removes that: every request carries its own version
  and capability info in _meta, so there's no session to lose.

  In the SDK, all of that lives in one object, *mcp.ClientSession. It holds the
  negotiated version and capabilities, the connection and the pending requests.
  It's already shaped like the era-dependent state we planned to track
  ourselves. So your code keeps exactly one thing per server:

  type mcpServer struct {      // sketch, not final
      name    string
      session *mcp.ClientSession
  }

  mcpTool then holds a pointer to the session plus the remote tool name, and
  calls session.CallTool. The era never shows up in your code.

  One thing that does remain yours: lifecycle. A session is a live process. So
  setupToolRegistry has to hand back a way to close them (session.Close()), and
  gracefulShutdown has to call it. Otherwise a spawned npx server outlives the
  agent. The kernel needs no change for this, but runAgent will have to own the
  list of sessions. I'd decide where that list lives as part of the next slice.

⏺ 1. Restart, and the idempotency problem

  Restarting the process is easy. Deciding whether to retry the call that was in
  flight is the hard part.

  If the server dies mid-tools/call, you can't tell whether it died before or
  after doing the work. For example, write_file may have written the file and
  crashed before replying. The rule I'd build:

  ┌────────────────────────┬────────────────────────────────────────────────┐
  │       Situation        │                     Action                     │
  ├────────────────────────┼────────────────────────────────────────────────┤
  │ Server is found dead   │ Restart, reconnect, then send the call.        │
  │ before a call is sent  │ Nothing was in flight, so this is safe.        │
  ├────────────────────────┼────────────────────────────────────────────────┤
  │ Server dies during a   │                                                │
  │ call, tool is          │ Restart and retry once.                        │
  │ read-only or           │                                                │
  │ idempotent             │                                                │
  ├────────────────────────┼────────────────────────────────────────────────┤
  │ Server dies during a   │ Restart, but don't retry. Return an error      │
  │ call, tool is not      │ observation: "server crashed; the call may or  │
  │ known to be safe       │ may not have completed. Check state before     │
  │                        │ repeating."                                    │
  └────────────────────────┴────────────────────────────────────────────────┘

  The model is a good fit for that last case. It can read the file or list the
  directory to find out what happened, which is the same recovery a person would
  do.

  MCP tools can advertise readOnlyHint, idempotentHint and destructiveHint in
  their annotations, and tools/list returns them. They give you the retry
  decision for free, with one caveat: the spec says they are hints from the 
  server, untrusted. A server can lie or just be wrong. That is fine for
  deciding whether to retry, but they must never be used to skip an approval
  check. The default when a hint is absent must be "not safe".

  Where it lives: inside mcpServer, not in the loop. It owns a mutex-guarded
  session and a reconnect(), and each mcpTool asks it for the current session.
  The kernel stays unaware, which fits your Tool-adapter design. In the
  stateless era a restart is trivial. For a legacy server it means a fresh
  handshake and a new session, so any server-side state from the old session is
  lost. That's one more reason to avoid tools that depend on it.

  I'll check which error the SDK returns when the connection is closed, so we
  detect crashes by something precise and not by string matching.

  ────────────────────────────────────────

❯ What is the cancel in lctx, cancel := context.WithTimeout(ctx,                
  10*time.Second) ?                                                             

⏺ cancel is a function that ends lctx early and releases the resources it holds.
  WithTimeout returns both the new context and that function.

  What WithTimeout creates

  context.WithTimeout(ctx, 10*time.Second) returns a child context that is
  cancelled when either of these happens first:
  - 10 seconds pass (the timeout)
  - the parent ctx is cancelled (Ctrl+C in your case)
  - you call cancel() yourself

  Internally it starts a timer. Calling cancel() stops the timer and detaches
  the child from its parent.

  Why you must call it

  Even if the call finishes in 50 ms and the timeout never fires, the timer and
  the parent-to-child link stay allocated until the 10 seconds run out. Calling
  cancel() right away frees them. go vet reports a "lost cancel" if you ignore
  it, and it's the most common context mistake.

  The standard idiom is to defer it on the next line:

  lctx, cancel := context.WithTimeout(ctx, 10*time.Second)
  defer cancel()
  res, err := srv.session.ListTools(lctx, nil)

  Calling cancel() after the work finished is harmless. It's safe to call more
  than once, and it doesn't affect results that were already returned.

  One caution for your main

  defer runs when the function returns, not at the end of the block. In main
  that's fine, because defer cancel() fires at the end of the program. But if
  you later create these contexts inside a loop (say, one per tool call), the
  deferred cancels would pile up until the surrounding function exits. In that
  case, put the work in a small helper function, or call cancel() explicitly
  after each call.

  Your existing code already has a parallel

  signal.NotifyContext(...) returned ctx, stop, and stop is the same idea. It's
  the cancel function for that context. WithCancel, WithTimeout, WithDeadline
  and NotifyContext all return one, and the rule is always the same: call it
  when you're done.

❯ So if I press Ctrl+C, that triggers stop() and cancel() ?                     
  ⎿  ⧉ Selected 4 lines from mcp_scratch.go in Visual Studio Code

⏺ No, it's the other way around. Ctrl+C cancels the contexts, and stop() and
  cancel() are cleanup functions that your code calls afterwards.

  What happens when you press Ctrl+C

  1. The OS sends your process SIGINT.
  2. Because of signal.NotifyContext, Go doesn't kill the process. It intercepts
     the signal and cancels ctx.
  3. lctx is a child of ctx, so it is cancelled automatically.
  4. Whatever is blocked on lctx (say, ListTools) wakes up and returns an error
     wrapping context.Canceled.
  5. Your code handles the error and main returns.
  6. Now the deferred cancel() and stop() run, in reverse order of the defer
     statements (cancel first, then stop).

  Cancelling flows down the tree from parent to child. A cancelled child doesn't
  cancel its parent.

  Ctrl+C ──► ctx cancelled ──► lctx cancelled ──► ListTools returns an error
                                                        │
                            main returns ◄──────────────┘
                                │
                       defers: cancel(), stop()

  The two cleanup functions

  ┌──────────┬────────────────┬─────────────────────────────────────────────┐
  │          │  Cancels the   │          What it does that matters          │
  │          │    context?    │                                             │
  ├──────────┼────────────────┼─────────────────────────────────────────────┤
  │ cancel() │ Yes, ends lctx │ Frees the timer and the link to the parent  │
  │          │  early         │                                             │
  ├──────────┼────────────────┼─────────────────────────────────────────────┤
  │          │ Yes, it also   │ Unregisters the signal handler, so Ctrl+C   │
  │ stop()   │ cancels ctx    │ returns to its normal behaviour of killing  │
  │          │                │ the process                                 │
  └──────────┴────────────────┴─────────────────────────────────────────────┘

  They'd run on a normal exit too, where nothing is cancelled and the program
  just finishes. They're there for cleanup, so they run on every path out.

  One gotcha: the second Ctrl+C

  After the first Ctrl+C, the signal stays captured until stop() runs. A second
  Ctrl+C is still swallowed and won't force-kill a stuck program. If the cleanup
  hangs, you'd have to use kill from another terminal. A common fix is to
  restore the default right after the first signal:

  go func() { <-ctx.Done(); stop() }()

  With that, a second Ctrl+C kills the process the normal way. It's optional for
  a scratch driver, but good practice for the real agent, where a stuck Close()
  would otherwise trap the user.

⏺ Correct, you don't implement them. The context and os/signal packages create

  ctx, stop := signal.NotifyContext(...)   // package gives you stop
  defer stop()                             // you just call it

  hand back a release function, and you defer it. Compare session.Close() from
  the MCP SDK and f.Close() for a file.

  The one place you'd write your own cancel function is context.WithCancel, when
  you want to cancel something yourself without a timeout or a signal. The
  package still builds the function for you, and you call it at the moment you
  decide the work should stop. In your own code, gracefulShutdown(cancel
