❯ for e.g. variable MaxTokens, the key name in config.anthropic.json is         
  max_tokens - how does Go know these are the same?                             
  ⎿  ⧉ Selected 1 lines from ../mvp1/main.go in Visual Studio Code

⏺ The struct tag. Look at the field declaration, not the name:

  MaxTokens int64 `json:"max_tokens"`

  That backtick string is a struct tag — a raw string literal attached to the
  field, stored in the type's metadata. It does nothing on its own; it's just a
  string that any library can read at runtime via reflection. The convention is
  key:"value" pairs, and encoding/json looks for the json key. So when
  json.Unmarshal walks the Config type, it sees field MaxTokens carries
  json:"max_tokens" and registers max_tokens as the wire name for it. Same
  machinery in both directions — json.Marshal would emit "max_tokens" too.

  Two things that follow from this:

  Tags are just strings, so typos are silent. Write json:"max_token" and nothing
  errors — the key in your config file simply never matches, and MaxTokens
  quietly keeps its default. This is the most common way a config field
  "mysteriously doesn't apply." go vet catches malformed tag syntax (missing
  quotes, bad spacing) but not a misspelled name.

  Without a tag, Go still tries. encoding/json falls back to matching the field
  name itself, case-insensitively. So an untagged MaxTokens would match
  "MaxTokens", "maxtokens", even "MAXTOKENS" — but not "max_tokens", because the
  underscore is a real character, not a case difference. That's exactly why
  every field here is tagged: Go's exported-field convention is MaxTokens,
  JSON's convention is max_tokens, and the tag is the adapter between the two.

  Only exported fields participate at all. A lowercase maxTokens is invisible to
  encoding/json — reflection can't set unexported fields — so it stays zero no
  matter what the JSON says, tag or not. That's the other silent failure mode.

  The // comments after some tags (// "openai" | "anthropic") are ordinary Go
  comments, outside the backticks, and have no effect on parsing.

  Is shell dangerous? Yes — it's the one tool with no ceiling

  The other builtins have a bounded blast radius by construction. shell doesn't:

  cmd := exec.CommandContext(ctx, "sh", "-c", in.Command)
  cmd.Dir = dir

  shell has no equivalent. The protections in tool/builtin.go are about runaway
  commands, not malicious ones: a 60s timeout, an output cap, a process-group
  kill so nothing outlives the call. None of that stops a single fast
  destructive command.

  failure is a confused model that misreads its task, or a prompt-injection
  payload sitting in a file it read a moment ago — tool output re-enters the
  context as an observation, so "this file told the agent to run X" is a live
  path.

  two reasons beyond safety. directory_tree gets the layout in one call instead
  of a dozen ls round-trips, read_multiple_files batches reads, and edit_file
  does surgical line edits instead of your write_file's whole-file overwrite.
  And the confinement is real: the server takes allowed directories as argv and
  refuses paths outside them, including via symlink. sh -c has nothing
  comparable.

  The one real gap: content search

  search_files is filename glob matching, not grep. There is no tool in that
  server that searches inside files. For codebase exploration that's the single
  most valuable primitive — "where is ContextBuilder implemented" is a content
  question, and without it the agent degrades to reading whole files hunting for
  a symbol, burning context fast. This is exactly why agents with only FS-MCP
  end up reaching for shell anyway.

  So the answer isn't "MCP instead of shell," it's: MCP for navigation and 
  reads, plus one narrow search tool, and then you can drop shell entirely for 
  read-only exploration.

  Filling the gap — three options

  1. A Go-native grep tool (my recommendation here). tool.Func with a {pattern, 
  path, glob} schema, implemented with regexp + io/fs.WalkDir, reusing the same
  path-confinement helper your read_file already has. ~40 lines, no subprocess,
  no new dependency, works identically on every platform, and it's a pure
  plug-in on the Tool axis — zero kernel changes. Downside: Go's regexp is RE2,
  so no backreferences or lookahead, and a naive walk over a large repo is
  slower than ripgrep and needs its own .git/node_modules skip list and match
  cap. For a teaching repo that's a feature — the skip list and the output cap
  are the interesting parts to write.

  2. Shell out to rg with a fixed argv. exec.Command("rg", "--json", "-m", 
  "200", pattern, dir) — never sh -c, so there's no shell metacharacter to
  inject through, and the model controls only the pattern and path, not the
  command. Fast and battle-tested. Downside: a hard dependency on ripgrep being
  installed (you have it at /opt/homebrew/bin/rg, but that's not portable), and
  you now own argument validation — a pattern starting with - is an argv
  injection unless you pass -- first.

  3. A second MCP server for search. Cleanest conceptually, but adds a process,
  a startup cost, and a dependency you don't control, for one tool. Not worth
  it.

  Option 1 or 2 both leave you able to set "tools": ["read_file", "write_file", 
  "grep"] and drop shell from the config entirely — at which point
  requires_approval only needs the write paths, and the read-only exploration
  loop runs without a single prompt. That's the real win: approval fatigue drops
  because the safe operations stopped needing approval.

  Name collisions. main.go:113 does tools[t.Spec().Name] = t after the builtins,

  // [agent] Never walked: huge, machine-generated, and a match inside one is
  // almost never what the model is looking for. .git alone will otherwise
  // dominate every result set.
  var skipDirs = map[string]bool{".git": true, "node_modules": true, "vendor":
  true}

  // Grep searches file contents under root for a regular expression.
  func Grep(root string) agent.Tool {
        return Func{Name: "grep",
                Description: "Search file contents for a regular expression. Returns matching 
  lines as path:line: text.",
                Schema: `{"type":"object","properties":{` +
                        `"pattern":{"type":"string","description":"RE2 regular expression"},` +
                        `"path":{"type":"string","description":"file or directory to search, relative 
  to the working directory; defaults to ."}},` +
                        `"required":["pattern"]}`,
                Fn: func(ctx context.Context, raw json.RawMessage) (string, error) {
                        in, err := Args[struct{ Pattern, Path string }](raw)
                        if err != nil {
                                return "", err
                        }
                        if in.Path == "" { // [agent] schema says optional, so supply the default here
                                in.Path = "."
                        }
                        // [agent] Compile, not MustCompile: a bad pattern from the model becomes a
                        // tool observation it can correct, not a panic that kills the agent.
                        re, err := regexp.Compile(in.Pattern)
                        if err != nil {

  fmt.Fprintf writes to anything that's an io.Writer. strings.Builder has a
  Write([]byte) (int, error) method, so it satisfies that interface — Fprintf
  formats the string and calls out.Write(...) under the hood. Same function
  you'd use with os.Stdout; the destination is just a buffer instead of a file.

  The & is required, not stylistic. Builder.Write is declared on a pointer
  receiver (func (b *Builder) Write(...)), so strings.Builder the value does not
  implement io.Writer — only *strings.Builder does. Passing out instead of &out
  is a compile error. That pointer receiver exists because Builder refuses to
  be copied after first use: it stashes its own address and panics with strings:
  illegal use of non-zero Builder copied by value if it detects a copy. Passing
  a pointer is how you avoid that.

  The closure sees the same variable. out is declared in the enclosing function,
  and the func(path string, d fs.DirEntry, err error) error literal closes over
  it by reference, not by copy. So every call WalkDir makes — once per file —
  appends to the one out, and after the walk finishes out.String() holds
  everything accumulated. That's why it's declared outside the callback rather
  than inside.

  If it reads more clearly to you, this is exactly equivalent:

  out.WriteString(fmt.Sprintf("%s:%d: %s\n", name, i+1, line))

  Fprintf is just the version that skips building the intermediate string.

  Why defer can't do it

        defer c.Close()        // never runs
        if err != nil { fatal(err) }   // os.Exit(1) → MCP server orphaned

  cleverer error helper — it's a structural split:

        ...
        if err := run(ctx, cfg, *q); err != nil {

        }
  }

  so every defer fires on the way out, and main is the only place that ever
  calls os.Exit. Note the three fatal() call sites are all in main — none in
  run. That discipline is the whole point; the helper is incidental.

  The one-liner you're asking about

  log.Fatal is the stdlib version, and you can delete the helper:

        log.Fatal(err)      // writes to stderr, then os.Exit(1)
  }

  not more defer-safe, just fewer lines.

  You'd want log.SetFlags(0) to suppress it, at which point you've written two
  lines to replace a three-line helper that also gives you a "fatal: " prefix.
  I'd keep fatal().

  Where defer genuinely earns its place

  Not for exiting — for adding context on every error path at once, using a

❯ what does signal.NotifyContext(context.Background(), os.Interrupt) do ?       
  ⎿  ⧉ Selected 1 lines from ../mvp1/main.go in Visual Studio Code

  Read 1 file, ran 2 shell commands (ctrl+o to expand)

⏺ ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
  defer stop()

  It turns Ctrl-C into a context cancellation instead of an abrupt process
  death.

  Piece by piece:

  - context.Background() is the root context — never cancelled, no deadline, no
    values. It's the parent you start from when nothing else is available.
  - signal.NotifyContext derives a child context from it and registers a signal
    handler. When one of the listed signals arrives, that child's Done() channel
    closes and ctx.Err() becomes context.Canceled.
  - os.Interrupt is SIGINT — what Ctrl-C sends. It's the portable spelling, so
    this works on Windows too, unlike syscall.SIGINT.
  - stop() unregisters the handler and restores the default behaviour. defer 
    stop() releases it on normal exit; without it you'd leak the handler and its
    goroutine.

  Why an agent cares

  That ctx gets threaded everywhere, so one Ctrl-C unwinds three different
  in-flight operations through the same mechanism:

  1. The LLM call — the HTTP request carries ctx, so it aborts mid-stream
     instead of waiting out a 60-second response.
  2. A running shell command — exec.CommandContext(ctx, "sh", "-c", ...) at
     tool/builtin.go:42, plus cmd.Cancel wired to killProcessGroup, so SIGKILL
     reaches the whole process group.
  3. A pending approval prompt — hooks/hooks.go:108:
  select {
  case line = <-lines:
  case <-ctx.Done():
      return fmt.Errorf("%s not approved: %w", c.Name, ctx.Err())
  }
     Cancellation denies the tool rather than leaving the goroutine blocked on
     stdin forever.

  Then the error propagates up out of run, and its defer c.Close() calls shut
  down the MCP servers. That's the same argument as the fatal() question: this
  design only works because nothing calls os.Exit from inside run.

  Contrast with the default: without NotifyContext, Go's runtime kills the
  process on SIGINT immediately — no defers, orphaned npx servers, a
  half-written .agent-memory.json.

  The gotcha worth knowing

  A second Ctrl-C won't force-quit. I tested it:

  pid=14485
  --- 2nd SIGINT ---
  STILL ALIVE after 2nd SIGINT
  ...
  exited normally

  NotifyContext keeps signal.Notify registered after it fires, and its internal
  channel has a buffer of 1 with nobody reading it any more. So the second
  SIGINT lands in that buffer and is swallowed. If your graceful shutdown hangs
  — say a tool is ignoring cancellation — you're stuck reaching for Ctrl-\
  (SIGQUIT) or kill -9 from another terminal.

  Most production CLIs handle this by calling stop() as soon as the first signal
  fires, so a second one gets the default behaviour and kills the process.
  Something worth considering for mvp2 once you have a REPL.

  Also note os.Interrupt is the only signal listened for here. A plain kill
  sends SIGTERM, which isn't in the list, so it terminates mvp1 abruptly with
  all the same orphaning problems. Adding syscall.SIGTERM to the argument list
  is a one-word fix — worth it if you ever run this under a process supervisor
  or in a container, where SIGTERM is the normal shutdown signal.

⏺ Correct on both counts. Two refinements worth having:

  "Graceful" is something you built, not something SIGTERM is. SIGTERM's default
  action is also immediate termination — same as SIGKILL from the program's
  point of view. The difference isn't gentleness, it's catchability: SIGTERM can
  be intercepted, so a program can choose to do cleanup first. Before you added
  syscall.SIGTERM to that list, kill <pid> killed mvp1 just as abruptly as kill
  -9. The grace came from registering the handler.

  kill -9 isn't "handled by the kernel" so much as acted on by it. The process
  is never notified at all — no handler, no defers, no flush of buffered output.
  The kernel just reclaims it.

  kill <pid>      → SIGTERM (15)  catchable  → your ctx cancels, defers run, MCP
  servers close
  kill -INT <pid> → SIGINT  (2)   catchable  → same path (Ctrl-C sends this)
  kill -9 <pid>   → SIGKILL (9)   uncatchable → gone; exit status 137

  One thing that surprises people: kill -9 does not kill the process's children.
  The kernel reclaims the parent's own resources — memory, file descriptors,
  locks — but any process it spawned keeps running and gets reparented to PID 1.
  So kill -9 on the agent leaves an npx MCP server alive indefinitely.

  That's precisely why tool.Shell doesn't rely on its own cleanup code running:

  cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}

  Putting the command in its own process group means a single kill can target
  the group (syscall.Kill(-pid, SIGKILL)) and reach everything it spawned. It's
  belt-and-braces for the case where your defers never get a chance.

❯ what happens when stop() is executed?                                         

⏺ Let me show it rather than describe it — this is also the fix for the
  double-Ctrl-C problem from earlier:

  Ran 2 shell commands (ctrl+o to expand)

⏺ stop() does exactly two things. From Go's source:

  func (c *signalCtx) stop() {
        c.cancel()
        Stop(c.ch)
  }

  1. It cancels the context. This is the part people miss — stop() isn't just
  cleanup, it's also a cancel. That's fine as defer stop() in main, since you're
  leaving anyway, but it means calling stop() early cancels everything
  downstream holding that ctx. It's idempotent, so calling it after a signal
  already fired is a no-op.

  2. It unregisters the channel via signal.Stop, which stops relaying those
  signals and restores the disposition they had before Notify was called. The
  watcher goroutine then exits through its case <-c.Done() branch instead of
  leaking.

  What that means in practice

  This is the fix for the double-Ctrl-C problem — call stop() as soon as the
  first signal fires, and the next one kills the process. I tested it with
  SIGTERM:

  1st signal -> ctx cancelled: context canceled
  stop() called; now doing slow cleanup...
  cleanup 0
  --- 2nd SIGTERM after stop() --- DIED on 2nd signal

  Cleanup stopped at cleanup 0 — the second signal got the default action and
  terminated the process. Exactly the escape hatch you want when a tool is
  ignoring cancellation.

  But I need to correct something I implied earlier. "Restores default behavior"
  is not quite right — it restores the prior disposition, whatever that was.
  The same test with SIGINT did not die:

  --- 2nd SIGINT after stop() --- still alive
  ... cleanup 0..4, exited normally

  Because a non-interactive shell sets SIGINT to ignored for background jobs,
  and Go preserves a pre-existing SIG_IGN rather than installing a handler over
  it. So stop() restored ignore, not terminate. In a real terminal where you
  press Ctrl-C, the prior disposition is the default terminate and the second
  one does kill. Worth knowing because it means this behaviour differs between
  an interactive session and something run under a supervisor or &.

  The shape for mvp2

  ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt,
  syscall.SIGTERM)
  defer stop()

  if err := run(ctx, cfg, *q); err != nil {
        fatal(err)
  }

  The defer stop() covers the normal-exit path. If you later want the force-quit
  escape hatch, you'd watch ctx.Done() in run and call stop() at the top of the
  shutdown path — at which point the second Ctrl-C bypasses your cleanup
  entirely, which is the point.

⏺ Because context cancellation in Go is cooperative, not preemptive. Cancelling
  a context doesn't stop anything — it closes a channel and it's up to your code
  to notice. time.Sleep takes no context and has no way to be interrupted, so
  it sleeps the full second regardless.

  Proof — same shape as your run, printing ctx.Err() after the sleep:

  after sleep, ctx.Err() = context canceled     ← the signal DID arrive
  printed anyway                                 ← Sleep didn't care

  The signal was delivered, NotifyContext cancelled ctx on time, and nothing was
  listening. Note your run never reads ctx at all — it's an unused parameter,
  which Go permits silently.

  The fix

  Make the wait itself cancellable:

  func run(ctx context.Context, cfg Config) error {
        select {
        case <-time.After(1 * time.Second):
        case <-ctx.Done():
                return ctx.Err()   // returns context.Canceled
        }

        fmt.Printf("Running agent with configuration: %+v\n", cfg)
        return nil
  }

  time.After gives you a channel instead of a block, so select can race it
  against ctx.Done().

  The general rule, which is the thing worth internalising before the agent loop
  lands: anything that blocks must either take a ctx or be raced against 
  ctx.Done() in a select. The stdlib is consistent about which is which —
  exec.CommandContext, http.NewRequestWithContext, sql.QueryContext all take
  one; time.Sleep, a bare channel receive, and bufio.Reader.ReadString don't.
  That last one is why mvp1's approval hook reads stdin on a goroutine and
  selects on ctx.Done() (hooks/hooks.go:105-112) — there's no cancellable stdin
  read, so it builds one.

  Your agent loop will have three such points: the LLM HTTP call, each tool
  call, and the approval prompt. Miss any one and Ctrl-C hangs until it
  finishes.
