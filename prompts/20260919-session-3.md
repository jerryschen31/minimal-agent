  sync/atomic (atomic.Bool and its CompareAndSwap) is one way. A
  mutex-protected bool is another.

⏺ Not global. Give it the narrowest scope that everything needing it can still
  reach.

  Why a plain bool doesn't work

  The natural first attempt is:

  if !compacting {      // 1. check
      compacting = true // 2. set
      go compact()
  }

  The check and the set are separate steps. Your main loop and the compaction
  goroutine run at the same time. If /compact and the auto-trigger both run step
  1 before either reaches step 2, both see false, and both start a compaction.
  Also, one goroutine writing a plain bool while another reads it is a data race
  under Go's memory model. go test -race will flag it, and the result is
  undefined even when it looks fine.

  What atomic.Bool gives you

  It makes the check and the set one indivisible operation:

  var busy atomic.Bool

  if busy.CompareAndSwap(false, true) {
      // I flipped it. I am the only one who got here. Start the work.
  } else {
      // It was already true. Someone else is compacting. Skip.
  }

  CompareAndSwap(old, new) means "if the value is currently old, set it to new
  and return true. Otherwise change nothing and return false." The hardware does
  it as one step, so two callers can never both get true. Exactly one caller
  wins the flip. Compare that with calling Load() and then Store(), which is the
  racy two-step version from above.

  Other methods you'll use:
  - busy.Store(false) releases it.
  - busy.Load() reads it. It's only good for display or logging, not for
    deciding to start work, because the value can change right after you read
    it.

  Where it should live

  Whoever starts a compaction needs to check the same flag. That's two places
  today: the auto-trigger and the /compact command. Both are inside runLoop. So
  a local variable there is enough:

  var compacting atomic.Bool // declared once in runLoop, before the for loop

  Don't declare it inside the for body. That would create a fresh flag every
  turn, and each check would trivially succeed.

  A caveat: an atomic.Bool must not be copied after first use (go vet flags
  this). Pass it by pointer, *atomic.Bool, as in the maybeCompact signature I
  suggested. Passing it by value gives the callee its own copy, and the guard
  silently stops working.

  Trade-off against the alternative. You could put the flag inside each window
  type, next to gen. Then the window itself would reject a second concurrent
  compaction, and no caller could forget the check. The downside is that you'd
  repeat it in four window types, and "a compaction is running" is really about
  your summarizing policy, not the window's storage. Your earlier decision was
  to keep policy out of the windows, and the local variable is consistent with
  that.

  The release: use defer

  go func() {
      defer compacting.Store(false)
      // ... summarize, Compact, print errors ...
  }()

  If the goroutine returns early on an error, or panics, the flag would stay
  true forever and compaction would silently never run again. defer guarantees
  the release on every exit path. Try to think of what happens to the flag if
  you put compacting.Store(false) at the end of the function body instead, and
  the summarize call returns an error halfway.

❯ CompareAndSwap() is a built-in method for atomic.Bool type variables?         

⏺ Yes. CompareAndSwap is a method on the atomic.Bool type in the standard
  sync/atomic package. You don't install or define anything.

  atomic.Bool was added in Go 1.19, so you need that version or newer. It has
  these methods:
  - Load() bool
  - Store(val bool)
  - Swap(new bool) bool, which sets the value and returns the old one
  - CompareAndSwap(old, new bool) bool

  Import it with "sync/atomic". The zero value is ready to use and starts as
  false, so var compacting atomic.Bool needs no constructor, just like
  sync.Mutex.

  One more thing: Swap would also work here. if !compacting.Swap(true) { ... }
  means "set it to true, and if it was false before, I got here first". It does
  the same thing as CompareAndSwap(false, true). I'd still use CompareAndSwap
  because it states the intent, "only flip false→true", directly in the call.

  Since the method comes from the type, your editor should autocomplete it after
  compacting.. To read the docs, run go doc sync/atomic.Bool in the terminal.

  Is Store(false) after the call equivalent to defer?

  In this code, yes, in practice. The goroutine has exactly one thing between
  the claim and the release, the compactChatHistory call. Nothing can return
  early before your Store. It also runs before the Fprintln, which is fine,
  since printing an error doesn't need the flag held.

  They differ in one case: a panic. defer runs even while a panic unwinds the
  goroutine, and a plain statement doesn't. But an unrecovered panic in any
  goroutine kills the whole program, so a stuck flag wouldn't matter here.
  That's why they're equivalent in practice.

  The real reason to prefer defer is future edits. Suppose someone (you in two
  weeks) adds if err != nil { return } above the Store, or a recover(), or a
  second early exit. The release silently gets skipped, and compaction quietly
  stops forever. defer placed on the line right after the claim can't be skipped
  by later edits. Same behavior today, and it fails safe:

  go func() {
      defer compactInProgress.Store(false)
      fmt.Println("Auto-compaction triggered...")
      ...
  }()

  Recall that this only works because it's inside the goroutine's own function
  literal. In the /compact case it was different: there the release had to be an
  explicit Store, since a defer would wait for runLoop to return.

  1. Guard order is right. Size check first, then the flag flip, so you never
