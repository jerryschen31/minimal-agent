  The ReAct loop is one function. Each step rebuilds the context from memory,
  calls the model (reason and plan), runs every requested tool concurrently on
  goroutines (act), and appends the results as observations. Plain text with no
  tool calls is the final answer. Tool failures, unknown tools, and policy
  denials all go back to the model as error observations so it can recover
  rather than crash.

  How each of your requested capabilities maps onto the seams:

  - Any LLM. The OpenAI adapter covers Ollama, vLLM, llama.cpp, LM Studio,
    OpenAI, Groq, OpenRouter and similar via one base_url setting. The Anthropic
    adapter shows a provider with a different wire shape fitting the same
    interface. A Native field on assistant messages lets an adapter replay its
    own turn verbatim, which preserves Anthropic thinking blocks across tool
    calls.
  - Tools. tool.Func wraps any Go closure or library call. tool/mcp.go is a
    dependency-free stdio MCP client, so one config line exposes every tool on
    any MCP server as <server>_<tool>.
  - Memory and context are separate harnesses. Memory is the truth. Context is a
    view of it. The window builder always cuts at a user turn so tool calls are
    never separated from their results.
  - Observability, tracing, eval, cost. All are a Hook with four callbacks. The
    logger is the seed.
  - Safety. Returning an error from BeforeTool denies the call. Approval prompts
    a human, allowlist enforces policy, file tools are confined to the workdir,
    and sandboxing is a tool swap rather than a rewrite.
  - Subagents. agent.Subagent exposes a fresh agent as a tool with its own
    memory. Because tool calls already run in parallel, several subagents run
    concurrently for free.

  Why Go, and your extensibility question

  Go wins on the things that make an agent an infrastructure component:
  concurrency shaped like the problem (goroutines and context for parallel
  tools, subagents, child MCP processes, timeouts, cancellation), a single
  static binary that drops into a sandbox container, a memory-safe runtime with
  a tiny dependency surface (this project has one dependency), and implicit
  interfaces so plug-ins need no framework import.

  On extensibility, your instinct is partly right. Python and TypeScript have
  far more prebuilt agent tool packages. Two things blunt that in practice.
  First, MCP is language-neutral by design: servers are separate processes or
  HTTP endpoints, so the entire MCP server ecosystem, mostly written in

  are compute-heavy or ecosystem-locked: PyTorch or scikit-learn inference,
  pandas-style data wrangling, PDF or document parsing libraries, and prebuilt
  LangChain or LlamaIndex tool collections. If your agent's job is data science
  or ML research, that is frequent and Python wins. If it is a coding, ops, or
  general assistant agent, I would estimate under one tool in ten, and the
  escape hatch is a 30-line Python MCP server wrapping the library.
