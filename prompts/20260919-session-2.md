⏺ The idea works, and it fits the code you already have. Here is how I'd
  stress-test it.

  Why it's a good idea: Summarizing is a slow LLM call. In that time new
  messages can be added, and in the ring buffer or offset windows old ones can
  be evicted. So "replace messages 0–N" by index would hit the wrong messages.
  Your marking approach identifies messages by what they are, not where they 
  are. That is the same problem Gen was meant to catch, solved more directly.

  A simpler way to get the same result: every ChatMessage already has a unique
  ID. So you may not need a replace flag on the message at all. When compaction
  triggers, record the IDs of the messages you're about to summarize. That can
  be a set, or just the ID of the last one, since the window is append-only and
  ordered. Then ReplaceOld keeps any message whose ID isn't in that set, and
  those are the new ones.

  Marks and ID sets behave the same when things go well. They differ when things
  go wrong:
  - Mark on the message: you mutate shared state, so you have to unmark on the
    failure path. If the summary call errors and you forget, the messages stay
    marked, and the next ReplaceOld will drop them wrongly. It also has to
    happen under the window's mutex.
  - ID set held by the caller: nothing is mutated. A failed summary just
    discards the set, and there's nothing to clean up.

  Edge cases to handle either way:
  1. What if some of the marked messages were already evicted by the time
     ReplaceOld runs? For example, the ring buffer wrapped during the summary
     call. Your "unmarked = new" rule should still hold, but check it.
  2. What if a second compaction starts while the first is still running? Marks
     can't tell the two apart. An ID set can.
  3. The new window needs to be [summary] + new messages. Keep the summary as a
     message with its own ID and a role that suits your provider, since some
     don't like a second system message.

  The mark and unmark bookkeeping is a cost, and it's what the ID version
  avoids. Which do you want to go with? Either way, try writing the ReplaceOld
  signature and body for one window type first, probably OffsetWindow because
  it's the simplest. I'll review it. A useful question to answer as you write
  it: what does ReplaceOld take as arguments, and what does it return if none of
  the marked messages are found?

  Timing is what matters:

  The ID set has to describe exactly the messages you sent to be summarized.
  Snapshot messages are a frozen copy, so building the set from them is always
  correct, whether you do it just after the snapshot or later. Building it from
  GetMessages() at replace time would be wrong. By then the window may hold new
  messages, and they'd get treated as compacted and dropped.

  So "right before we create the new window" is fine only if you build it from
  the snapshot's Messages, never from the live window. Building it immediately
  after Snapshot() is safer, because the set and the summarize input then come
  from the same source and can't drift apart.

  Why not inside Snapshot():

  - Snapshot() is a generic view of the window (messages plus Gen). Adding a
    compaction-specific ID set makes it do two jobs. Each of the four window
    types would then have to build the set too, and that's duplicated code.
  - The set is derived data. Anyone holding Messages can compute it in about 3
    lines, so it doesn't need to come from the window.

  The downside of building it outside is that you compute the set even if you
  later abandon the compaction. That costs almost nothing.

  Suggested flow:

  1. state := window.Snapshot()
  2. Build compacted := map[string]struct{}{} from state.Messages.
  3. Call summarizeChatHistory(ctx, p, state.Messages).
  4. On success, call window.ReplaceOld(summaryMsg, compacted). That method
     keeps any message whose ID is not in compacted.

❯ Does Snapshot() need to return an error as a second return type, in case      
  something goes wrong in the Snapshot?                                         

⏺ No. In Go, a function returns an error only when it has a real way to fail,
  and your Snapshot() doesn't. It takes the mutex, copies a slice into a fresh
  one, and returns it. Copying into a new slice can't fail. An out-of-memory
  error would panic and never come back as an error anyway.

  An unneeded error return also has a cost. Every caller has to write state, err
  := ...; if err != nil {...} for a branch that can never run. That's noise,
  and it hints to readers that a failure mode exists when it doesn't.

  When it would become worth it: if a window type's state lives somewhere that
  can fail to read, such as a file or a database. Your mvp1 memory.File is that
  case, because reading it can hit disk errors. Your four windows are all
  in-memory, so they don't.

  Changing the signature later is cheap, because the compiler flags every
  caller. So don't add it defensively now. If you ever add a persistent window,
  you'd change the interface then, and only that implementation would actually
  return non-nil errors.

  Also, the failure you should be checking for is not from Snapshot(). It's the
  Gen mismatch from ReplaceOld. That's a normal outcome that needs handling, not
  an error in the "something broke" sense. Have you decided whether it comes
  back as a bool or as an error?

  problems, one design gap, and a small point about argument order.

  1. Bugs

  - ID type mismatch. ChatMessage.ID is a string, but you declared
    map[int]struct{}. That won't compile. Use map[string]struct{}.
  - summary is a string, not a ChatMessage. summarizeChatHistory returns text.
    If Compact takes the summary as a message, you need to wrap it first: give
    it a Role, a Content, a fresh ID from createID(), and a Timestamp. Otherwise
    the window ends up holding a message with an empty ID and role. Decide
    whether Compact receives the finished message (my recommendation, so the
    window doesn't need to know about roles or IDs) or the raw string.

  2. Design gap: Gen is missing

  You take state but never use state.Gen. The /clear and overlapping-compaction
  cases we discussed can't be detected without it. Compact should take
  state.Gen, and its result should tell you whether it applied. Right now you
  discard whatever it returns.

  3. The struct{}{} hash set

  Go has no built-in Set type. The idiom is a map where you only care about the
  keys:

  - map[string]struct{} means keys are strings and values are struct{}.
  - struct{} is an empty struct type. It has no fields, so it takes zero bytes.
  - struct{}{} is a value of that type. The first {} belongs to the type, and
    the second {} is the literal that creates one.

  So set[id] = struct{}{} reads as "store the key with a zero-size placeholder
  value". Lookup uses the map's two-value form:

  if _, found := set[id]; found { ... }

  You could use map[string]bool instead, and that's fine. It costs one byte per
  entry and reads a bit more naturally (if set[id]). The struct{} version
  signals "this is a set, values are meaningless", and it's what you'll see in
  most Go code. The honest downside is that it looks odd at first, which is what
  you noticed. At 10 messages, performance doesn't matter, so pick whichever
  you find clearer.

  4. Arguments to Compact()

  Compact(stateMessageIDs, summary) needs one more: state.Gen. I'd suggest this
  shape, and the return type is yours to settle:

  Compact(ids map[string]struct{}, summary ChatMessage, gen int) bool

  Your existing style is ctx, p, w, while this function has ctx, w, p. That's a
  minor point, but keep the order consistent across functions.

  One more thing to check when you write Compact itself: the summary should go
  first in the new window, followed by the surviving messages in their original
  order. Also make sure the compacted set is a contiguous prefix, so you don't
  split a tool-call and result pair when you get to the mvp1 tool-calling stage.
