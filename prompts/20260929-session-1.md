  Does order matter for correctness?

  No. The model treats the tool list as a menu. A different order on the next
  request causes no error and no functional problem. My "must" should have been
  "should", and only for the reasons below.

  What "a stable prompt prefix is cacheable" means

  Providers speed up and discount repeated requests by caching the work they've
  already done on the start of the prompt:
  - Anthropic's prompt caching and OpenAI's automatic caching both match on an
    exact prefix. The prompt is processed in order (tools, then system prompt,
    then messages), and the cache covers however many leading tokens are
    byte-identical to an earlier request.
  - Local servers like Ollama do something similar with their KV cache.

  Tool definitions sit at the front of that sequence. If the tool order changes
  between requests, the very first tokens differ. The prefix match then fails at
  the start, and the whole conversation after it is reprocessed at full price
  and latency, even though the messages are identical. In a ReAct loop you make
  many calls per turn with a growing but otherwise identical prefix, so that is
  where caching pays off most.

  Sorting is only there to make the bytes identical each time, because Go's map
  iteration order is random.

  Is the O(n log n) sort a real cost?

  No, but you're right that sorting on every request is the wrong shape. With n
  around 5 to 50 tools, the sort takes microseconds. The Chat call takes
  seconds, so it's noise. The design smell is real, though: the tool set changes
  only when someone registers a tool or runs /mcp-add or /mcp-remove, so
  recomputing on every request does work that can't have changed.

❯ I've never seen sync.RWMutex - how is this different from a normal            
  sync.Mutex? Keep your answer brief.                                           

⏺ A sync.Mutex allows one goroutine at a time in the critical section, whether
  it reads or writes.

  A sync.RWMutex has two modes:
  - RLock/RUnlock (read lock): any number of goroutines can hold it at the same
    time.
  - Lock/Unlock (write lock): exclusive. It waits for all readers to leave and
    blocks new readers and writers until it is released.

  r.mu.RLock()         // many readers OK simultaneously
  defer r.mu.RUnlock()

  Why use it here: Defs() and Lookup() run on every request and are read-only,
  while writes happen only on /mcp-add or /mcp-remove. With a plain Mutex,
  concurrent readers would queue up for no reason.

  Downside: RWMutex has more bookkeeping than Mutex, so it is slightly slower
  per operation. It only wins when reads are frequent, reads are held for a
  non-trivial time, and readers actually run concurrently. Today only one
  goroutine reads the registry, so a plain Mutex would work just as well. I
  suggested RWMutex because the read-heavy, write-rare shape is exactly its use
  case. If you'd rather keep things simple until concurrency shows up,
  sync.Mutex is a fine choice. Swapping later means changing the field type and
  the RLock calls.

  Rule of thumb: don't take a write lock while holding a read lock on the same
  RWMutex. It deadlocks, because the write lock waits for your own read lock to
  release.

  Adding recover()

  Concepts:
  - A panic unwinds the stack, running deferred functions on the way. recover()
    stops the unwinding and returns the panic value, but only when it is called
    directly inside a deferred function, in the same goroutine that panicked.
  - A deferred function can't return a value for its caller. It can assign to a
    named return value. That is how you turn a panic into an ordinary error.

  Small example:
  func safe() (err error) {           // named return, so the deferred func can 
  set it
        defer func() {
                if r := recover(); r != nil {       // r is whatever was passed to panic()
                        err = fmt.Errorf("panic: %v", r)
                }
        }()
        panic("boom")
  }

  runToolCall. A panic then becomes a normal error, and it flows into the if err
  != nil branch you already have. Recovery lives in one place, and
  runToolCall's shape doesn't change.

  Decisions and trade-offs:

  - What does the model see? Something short like error: tool panicked: <value>.
    Don't send a stack trace to the model: it wastes tokens and exposes
    internals. If you want the trace (runtime/debug.Stack()), write it to
    cs.OutBuffer for yourself, and pass cs in or return it.
  - What recover doesn't cover:

      process, because recover only covers its own goroutine.
    - Fatal runtime errors (concurrent map writes, out of memory, deadlock)
      aren't recoverable panics at all.

    model, so make sure you see it somewhere, such as the debug output or a log
    line.

    mid-write, that state stays broken. That is worth knowing when MCP or shell
    tools arrive.

❯ what is toolCallID used for again?                                            

⏺ toolCallID links a tool result back to the specific tool call that asked for
  it.

  Why it exists: in one reply the model can request several tool calls, for
  example two read_file calls. Your results come back as separate role:"tool"
  messages, and the model needs to know which result answers which call. The
  provider assigns each call an id (like call_abc123), and you echo it on the
  result as tool_call_id:

  assistant: tool_calls: [ {id:"call_1", read_file {"path":"a.txt"}},
                           {id:"call_2", read_file {"path":"b.txt"}} ]
  tool:      tool_call_id:"call_1", content:"<contents of a.txt>"
  tool:      tool_call_id:"call_2", content:"<contents of b.txt>"

  The rules:
  - Only role:"tool" messages set it. The value is call.ID from the ToolCall
    being answered. That is why runToolCall passes call.ID.
  - Every ToolCall needs exactly one tool message with a matching tool_call_id.
    Providers reject a request with an unanswered call or an orphan result. That
    is the reason runToolCall always returns a message, even on failure.
  - User and assistant messages leave it empty (""). The assistant message
    carries the calls in ToolCalls, and the tool messages answer them by ID. The
    field is omitempty, so it disappears from the JSON for other roles.

  The pairing:

  ┌───────────┬─────────────────┬────────────────────────┐
  │  Message  │  Field it uses  │       Points to        │
  ├───────────┼─────────────────┼────────────────────────┤
  │ assistant │ ToolCalls[i].ID │ defines the ID         │
  ├───────────┼─────────────────┼────────────────────────┤
  │ tool      │ ToolCallID      │ refers back to that ID │
  └───────────┴─────────────────┴────────────────────────┘

  It is also what lets the context window and compaction, later on, check that
  they never separate a call from its results.
