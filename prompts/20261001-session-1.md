  1. Config. Today Config.Tools []string is only a placeholder. A server needs a
  label (it becomes the tool-name prefix), a transport kind, and either
  Command/Args/Env for stdio or URL for HTTP later. Keep the JSON tags
  consistent with the rest of Config.

  2. mcpServer. Your scratch version holds name and session. The decided changes
  are:
  - Replace command/args with a newTransport func() mcp.Transport factory. A
    closed transport can't be reused, and HTTP has no process to respawn.
  - Add a sync.Mutex guarding session, because reconnect() swaps it while tool
    calls run concurrently.
  - Connect with its own longer timeout, since a cold npx download is slow.

  3. mcpTool. This needs a pointer receiver, and it holds three things:
  - A pointer back to its *mcpServer.
  - The remote name, and the prefixed <label>_<name> name that the model sees.
  - A ToolDef captured once at list time, plus a safeToRetry bool derived from
    the annotations. ToolAnnotations is a pointer, so a nil value or missing
    hint means false.

  Only mcpServer is shared across tools. A reconnect then fixes every tool of
  that server at once.

  4. Shutdown ownership. setupToolRegistry currently returns only the registry,
  so nothing holds the sessions. Either it also returns []*mcpServer, or
  ChatSession gets a field. A leaked npx process is the failure to avoid.

  5. Prompts and resources (my proposal). MCP has three primitives, and the
  difference is who controls each one:

  ┌──────────────────┬─────────────┬────────────────────────────────────────┐
  │    Primitive     │ Controlled  │           Fits your agent as           │
  │                  │     by      │                                        │
  ├──────────────────┼─────────────┼────────────────────────────────────────┤
  │ Tools            │ the model   │ Tool in the registry (steps 1–3 above) │
  ├──────────────────┼─────────────┼────────────────────────────────────────┤
  │ Resources (read  │ the         │ a /mcp-resources and /mcp-read <uri>   │
  │ by URI)          │ app/user    │ slash command that injects the content │
  │                  │             │  as a message                          │
  ├──────────────────┼─────────────┼────────────────────────────────────────┤
  │ Prompts          │             │ a slash command per prompt, whose      │
  │ (templates with  │ the user    │ returned messages go into the turn     │
  │ args)            │             │                                        │
  └──────────────────┴─────────────┴────────────────────────────────────────┘

  My recommendation is to build no resource or prompt types yet.
  - Why not: neither fits the model-driven Tool path, each needs a UI decision
    in your slash-command handler, and you can't test them against the
    filesystem server. It advertises tools only, but check this with
    session.InitializeResult().Capabilities, where a nil Resources or Prompts
    field means unsupported.
  - What to do instead: make sure mcpServer exposes the session cleanly, so
    these can be added later as methods without a redesign. When you reach step
    4 (/mcp-* commands), add a short DECISIONS.md entry for them.
  - Downside: if you later want the model itself to read resources, you'd wrap
    ReadResource as a generic tool. That's a small adapter, but it is a design
    change.
  - What would flip this: a server you actually want to use that exposes
    resources or prompts.

  I haven't checked the SDK's exact method names for the other primitives
  (ListResources/ReadResource, ListPrompts/GetPrompt, or paging iterators like
  session.Tools). Verify them with go doc when you get there.

⏺ Yes to both: infer the transport from which fields are present, and set it per
  server.

  1. Inferring the transport, per server

  Each entry under mcpServers is its own server with its own transport, and each
  mcpServer gets its own transport factory. A mix of stdio and HTTP servers in
  one file is normal.

  The rule is simple:

  ┌──────────────────┬─────────────────────────────────┐
  │  Fields present  │            Transport            │
  ├──────────────────┼─────────────────────────────────┤
  │ command          │ stdio                           │
  ├──────────────────┼─────────────────────────────────┤
  │ url              │ Streamable HTTP                 │
  ├──────────────────┼─────────────────────────────────┤
  │ both, or neither │ config error, naming the server │
  └──────────────────┴─────────────────────────────────┘

  The trade-off: other tools differ. Claude Desktop and Cursor infer, as you
  propose. Claude Code's .mcp.json and VS Code use an explicit "type": "stdio" |
  "http" | "sse". The explicit form exists because legacy SSE servers also use
  a url, so a URL alone is ambiguous between SSE and Streamable HTTP. You only
  plan to support Streamable HTTP, so inferring is unambiguous for you.

  My recommendation is to infer, and to accept an optional type that you
  validate against the fields (a "type": "http" entry with a command is an
  error). That makes files copied from other tools load. The trigger to make
  type required is if you ever add legacy SSE.

  2. HTTP server config

  There is no official standard for this file. The MCP spec defines the
  transports and not the client config format, so mcpServers is a convention
  that clients copied from Claude Desktop. This is from memory of the common
  shapes, so check it against the docs of any tool you want compatibility with:

  {
    "mcpServers": {
      "remote": {
        "type": "http",
        "url": "https://example.com/mcp",
        "headers": { "Authorization": "Bearer <token>" }
      }
    }
  }

  - type is optional in the inferring clients.
  - headers is the usual place for a static token.
  - OAuth isn't configured here. It runs as a flow at connect time, which is
    your step 5.
  - VS Code names the top-level key servers, not mcpServers.

  3. Where env goes

  env is a sibling of command and args, inside the server object. It maps string
  keys to string values:

  "github": {
    "command": "npx",
    "args": ["-y", "@modelcontextprotocol/server-github"],
    "env": { "GITHUB_TOKEN": "..." }
  }

  child would lose PATH, and npx would not be found. Use cmd.Env = 
  append(os.Environ(), "KEY=value", ...) instead.

  api_key_name field already stores the name of an env var rather than its

⏺ Mostly true, with two exceptions. For the transport you're about to use,
  requests to a remote server are POSTs.

  Why it's POST even for something read-only like list_directory

  MCP messages are JSON-RPC. list_directory is not an HTTP route. It's a tool
  name inside the body of a tools/call request:

  POST /mcp
  Content-Type: application/json
  Accept: application/json, text/event-stream

  {"jsonrpc":"2.0","id":7,"method":"tools/call",
   "params":{"name":"list_directory","arguments":{"path":"/tmp"}}}

  In JSON-RPC the operation lives in method and params, and the HTTP verb
  carries no meaning. HTTP is only the pipe, just as stdin and stdout are for
  the stdio transport. Your LoggingTransport output from the scratch driver
  shows the same JSON, and over HTTP only the delivery changes. REST uses GET to
  mean "safe read". MCP's transport has no way to express that, so everything
  goes over one endpoint as a POST.

  Where "always POST" isn't quite true

  For Streamable HTTP, from my recollection of the spec:

  ┌────────┬─────────────────────────────────────────────────────────────────┐
  │  Verb  │                            Used for                             │
  ├────────┼─────────────────────────────────────────────────────────────────┤
  │        │ every client→server message: requests (tools/call, tools/list,  │
  │ POST   │ initialize) and notifications. The server answers with plain    │
  │        │ JSON, or with an SSE stream if it wants to send progress or     │
  │        │ other messages before the final result.                         │
  ├────────┼─────────────────────────────────────────────────────────────────┤
  │        │ optional. The client opens a long-lived stream so the server    │
  │ GET    │ can push messages on its own, such as list-changed              │
  │        │ notifications.                                                  │
  ├────────┼─────────────────────────────────────────────────────────────────┤
  │ DELETE │ optional. The client ends a session.                            │
  └────────┴─────────────────────────────────────────────────────────────────┘

  For legacy SSE it is split differently. The client does a GET to open an event
  stream, the server announces a separate POST URL, and every request goes to
  that URL as a POST.

  So your agent's session.CallTool is a POST over both HTTP transports. The
  first sentence of what the chat agent told you holds for client requests, but
  it overlooks the GET stream and DELETE.

  Why it matters for your design

  Because the verb tells you nothing, nothing at the HTTP layer says whether a
  call is safe to retry or cache. That is the reason the tool annotations
  (readOnlyHint, idempotentHint) exist, and why your restart rule in
  DECISIONS.md depends on them rather than on anything the transport provides.

  session handling and headers like Mcp-Session-Id may differ. For anything

⏺ MCPServerConfig doesn't exist in the file yet, so this is a design question.

  Does a remote server have env?

  No. env sets environment variables for the process you spawn. A remote server
  is not your child process, so there is nothing for it to configure. A remote
  server's credentials go in headers, or in OAuth later. Some people copy an env
  block onto a remote entry thinking it passes a token. That fails silently if
  you ignore the field.

  Recommended shape: one flat struct

  type MCPServerConfig struct {
        Type string `json:"type,omitempty"` // optional: "stdio" | "http" | "sse"

        // local (stdio)
        Command string            `json:"command,omitempty"`
        Args    []string          `json:"args,omitempty"`
        Env     map[string]string `json:"env,omitempty"`

        // remote (HTTP)
        URL     string            `json:"url,omitempty"`
        Headers map[string]string `json:"headers,omitempty"`
  }

  All fields are optional. Which ones are set decides the transport, and a small
  method validates them.


  ┌───────────┬──────────┬─────────────────────────────────┬────────────────┐
  │ Transport │ Required │            Optional             │ Must be empty  │
  ├───────────┼──────────┼─────────────────────────────────┼────────────────┤
  │ stdio     │ command  │ args, env                       │ url, headers   │
  ├───────────┼──────────┼─────────────────────────────────┼────────────────┤
  │ http      │ url      │ headers                         │ command, args, │
  │           │          │                                 │  env           │
  ├───────────┼──────────┼─────────────────────────────────┼────────────────┤
  │ sse       │ url      │ (skipped with a warning, so no  │                │
  │           │          │ further checks)                 │                │
  └───────────┴──────────┴─────────────────────────────────┴────────────────┘

  Any other combination is a config error naming the server: both command and
  url, neither of them, or a type that contradicts the fields.

  Why I'd make a stray env on a remote server an error and not a warning: it's a
  known field that doesn't apply, which is different from the typo-style
  unknown keys that only warn. If you ignored it, the token would silently never
  be sent, then you'd get a 401, and under warn-and-skip that would just look
  like a connection failure.

  Alternatives I'd reject, and one variant

  - Nested per transport ({"stdio": {...}, "http": {...}}): this breaks the
    shape every other MCP client uses, so copied configs wouldn't load.
  - Separate Go types plus a custom UnmarshalJSON: this is the "parse, don't
    validate" style. After load, an invalid state can't be represented, and the
    connect code does a type switch. It's more types and code for two
    transports. Switch to it if you add a third transport, or if connect code
    starts re-checking fields.
  - Variant: embedded structs. encoding/json flattens embedded structs, so you
    can group the fields in Go (StdioConfig, RemoteConfig) and keep the flat
    JSON. The downside is that struct literals in tests become more verbose.
    It's worth it once fields multiply, for example per-transport timeouts or
    OAuth settings. I'd wait for that.

  Where the validation lives

  Keep it as a pure method with the signature from DECISIONS.md,
  (MCPServerConfig) transportKind() (string, error). It returns "stdio", "http"
  or "sse". The loop in setupToolRegistry calls it for each server in sorted key
  order, wraps any error with the label (mcpServers["fs"]: ...), and:
  - returns the error for a shape error (that is what DECISIONS.md says);
  - warns and skips for "sse";
  - calls connectMCP with a transport factory built per kind for the others.

  This avoids a separate Validate step, and it fits your plan to do heavier
  config checking later.

  Two gotchas

  - Typos inside a server entry ("arg" for "args") are silently dropped. The
    nested unknown-key warning from the open list in DECISIONS.md is what would
    catch them.
  - Merge versus replace: json.Unmarshal merges map entries into an existing
    map. If you ever put a default server in getDefaultConfig(), a file's
    mcpServers adds to it and doesn't replace it. Leave the default MCPServers
    nil.

  the file, it fills each McpServerConfig in the map from the JSON. A

  when code builds a struct by hand, like your NewToolRegistry. Here the file is
  the only producer.

  inferred kind can be derived from the other fields at any moment, so storing
  it creates a second copy that can go stale or disagree with them. Type should
  keep meaning "what the user wrote in the file". That also keeps /config output
  faithful to the file.

  for _, label := range slices.Sorted(maps.Keys(cfg.McpServers)) { // sorted:

        case "stdio": // build the exec transport factory
        case "http":  // build the Streamable HTTP factory

⏺ No. *mcp.CallToolParams is the SDK's struct for the whole tools/call request,
  and your args is only one field inside it:

  type CallToolParams struct {
        Name      string `json:"name"`                // which tool: the server-side 
  name, so t.toolName
        Arguments any    `json:"arguments,omitempty"` // the tool's arguments: your 
  args goes here
        // plus Meta, InputResponses, RequestState (leave these empty)
  }

  You build it yourself and pass a pointer:

  &mcp.CallToolParams{Name: t.toolName, Arguments: args}

  Arguments is an any, and the SDK marshals it into the JSON request. A
  json.RawMessage marshals as itself, so it goes through unchanged. The tool
  name is on the struct because the server needs to know which tool to run, and
  your args only says how.

⏺ You can't defer out of a function, because a defer runs when the function that
  contains it returns. A defer s.Close() inside connectLocalMCP would close the
  server the moment you get it back.

  The usual Go pattern is that whoever receives the resource closes it.
  connectLocalMCP already returns the *mcpServer, which has a Close() method, so
  the owner is runAgent. It defers one cleanup right after setup:

  mcpServers, err := setupMCPServers(ctx, cfg)
  // ... print the error if any ...
  defer closeMCPServers(mcpServers) // runs when runAgent returns, on every path

  // a small helper, not a method:
  func closeMCPServers(servers []*mcpServer) {
        for _, s := range servers {
                if err := s.Close(); err != nil {
                        // print a warning; keep closing the rest
                }
        }
  }

    setup steps. If setupToolRegistry fails and runAgent returns early, the
    servers still get closed.
